# 辰光 Agent 平台管理前端设计

## 1. 目标

在 `app/` 目录实现一个面向桌面 B/S 场景的管理后台，只覆盖 `swagger-openapi.json` 当前已提供的接口：登录、验证码、用户、角色、权限和健康检查。不创建 Agent、模型、知识库或工作流等无后端接口的占位功能。

## 2. 技术方案

- React + Vite + TypeScript；
- shadcn/ui + Tailwind CSS；
- React Router 管理前端路由；
- TanStack Query 管理服务端数据、缓存和刷新；
- React Hook Form + Zod 管理表单与校验；
- Vitest + React Testing Library 测试核心行为；
- 手写类型化 API 客户端，不生成 OpenAPI 客户端代码。

采用手写 API 客户端是因为当前接口数量有限，并且存在 HTTP 200 承载业务错误、角色 CRUD 路径重复等项目特有约束。客户端必须严格使用 `swagger-openapi.json` 中的当前路径。

## 3. 产品范围

### 3.1 登录

- 首次进入受保护页面时跳转登录；
- 页面包含用户名、密码、验证码图片和验证码输入；
- 进入页面及手动刷新时请求新验证码；
- 登录提交 `username`、`password`、`captcha_code`、`captcha_key`；
- 成功后保存 JWT，并请求 `/api/v1/users/me` 验证登录态；
- 验证码错误或过期后自动刷新验证码；
- 退出登录时清除本地令牌和 Query 缓存。

### 3.2 概览

- 显示 `/health` 的服务状态；
- 并行请求用户、角色和权限列表第一页，通过 `total` 显示真实总数；
- 提供用户、角色、权限管理的快捷入口；
- 不展示后端无法提供的趋势、用量或 Agent 数据。

### 3.3 用户管理

- 分页、关键词搜索；
- 创建用户；
- 查看用户基础信息；
- 查看用户角色；
- 通过 JSON 角色 ID 数组整体替换用户角色；
- 不提供后端不存在的用户编辑、删除和启停操作。

### 3.4 角色管理

- 分页、关键词搜索；
- 创建、查看、编辑和删除角色；
- 查看角色当前权限；
- 通过 `permission_ids` 整体替换角色权限；
- CRUD 使用当前接口路径 `/api/v1/roles/roles`；
- 权限分配使用 `/api/v1/roles/{role_id}/permissions`。

### 3.5 权限管理

- 分页、关键词搜索；
- 创建、查看、编辑和删除权限；
- 权限编码创建后不可修改。

## 4. 信息架构

```text
/login                  登录
/
└─ /overview            概览
└─ /users               用户管理
└─ /roles               角色管理
└─ /permissions         权限管理
```

应用采用固定侧边栏、顶部工具栏和主内容区。侧边栏约 224px，顶部栏约 56px。窄屏下侧边栏切换为抽屉，保证基础查看和操作，但首要体验是桌面端。

## 5. 视觉设计

设计目标是成熟、克制、信息优先的企业后台，避免常见 AI 生成感。

- 中性灰、墨色和白色为主，暖金色只用于主操作、焦点和当前导航；
- 普通内容不使用渐变、玻璃拟态、光晕和装饰性插画；
- 圆角控制在 6–8px；
- 普通内容不使用悬浮阴影，阴影只用于弹窗、下拉菜单和抽屉；
- 不把每个区域都包装成 Card，优先用标题、留白、分隔线和表格组织内容；
- 正文与表格以 14px 为主，页面标题保持克制；
- 表格采用紧凑密度，工具栏与分页位置保持稳定；
- 登录页使用单列窄表单，不做营销式左右分屏；
- 不使用虚假图表、巨型数字、胶囊标签堆叠或宣传性文案。

## 6. 组件设计

### 6.1 应用框架

- `AppShell`：侧边栏、顶部栏、移动端导航；
- `PageHeader`：页面标题、说明和主要操作；
- `DataToolbar`：搜索、刷新和新建操作；
- `DataPagination`：页码、每页数量和总数；
- `ProtectedRoute`：令牌检查和登录跳转。

### 6.2 业务组件

- 用户创建表单、用户详情、角色分配抽屉；
- 角色创建/编辑表单、角色详情、权限分配抽屉；
- 权限创建/编辑表单、权限详情；
- 删除确认对话框；
- 服务状态和真实数量摘要。

优先使用 shadcn/ui 已有组件：Button、Input、Field、Table、Sheet、Dialog、AlertDialog、Badge、Skeleton、Empty、Pagination、DropdownMenu、Sidebar 和 Sonner。表单必须显示字段级错误，弹窗和抽屉必须包含可访问标题。

## 7. 数据与状态流

### 7.1 API 客户端

统一请求层负责：

- 从 `VITE_API_BASE_URL` 读取服务端地址，默认使用同源相对路径；
- 自动附加 `Authorization: Bearer <token>`；
- 解析统一 `{code, message, data}` 响应；
- HTTP 非成功、业务 `code !== 200` 和 FastAPI 422 均转换为统一错误；
- 收到认证失败时清除令牌并跳转登录；
- 支持 `AbortSignal`，避免页面卸载后的无效更新。

### 7.2 查询缓存

- 用户、角色、权限分别使用稳定 Query Key；
- 搜索词、页码和每页条数进入 Query Key；
- 创建、编辑、删除和分配成功后只失效相关查询；
- 概览统计并行加载，单项失败不阻塞其他统计显示。

### 7.3 本地状态

- JWT 以带版本号的最小结构保存在 `localStorage`；
- 不持久化用户列表、角色列表或权限列表；
- 搜索、分页、弹窗开关保留在对应页面局部状态；
- 不引入额外全局状态库。

## 8. 错误与反馈

- 页面初始加载显示 Skeleton；
- 无数据使用 Empty；
- 查询失败显示可重试 Alert；
- 创建、更新、删除和分配结果使用 Sonner；
- 删除前使用 AlertDialog 明确对象名称；
- 表单提交期间禁用提交按钮并显示 Spinner；
- 验证码错误或登录失败保留用户名，清空密码并刷新验证码；
- 不在界面中暴露堆栈、原始响应或令牌。

## 9. 本地联调

Vite 开发服务器将 `/api` 和 `/health` 代理到 `http://127.0.0.1:8000`。生产环境通过 `VITE_API_BASE_URL` 或反向代理配置后端地址。

前端不修复后端契约问题，但会兼容：

- 业务异常可能使用 HTTP 200；
- 角色 CRUD 的重复 `/roles/roles` 路径；
- 用户角色分配请求体是裸 ID 数组；
- 角色权限分配请求体是 `{ "permission_ids": [...] }`；
- 用户角色查询返回单元素数组。

## 10. 测试策略

- API 客户端：业务错误、HTTP 错误、422 错误、令牌注入；
- 登录：验证码加载、刷新、提交成功、失败后刷新；
- 路由保护：无令牌跳转登录；
- 列表：搜索、分页、加载、空状态和错误重试；
- 用户角色与角色权限分配：初始选中、整体替换、成功后刷新；
- 删除：确认前不请求，确认后执行并刷新列表；
- 最终执行单元测试、TypeScript 检查和 Vite 生产构建。

## 11. 验收标准

- 所有代码位于 `app/`；
- 可以完成登录、退出及登录态保护；
- 可以完成 Swagger 已有的所有用户、角色和权限操作；
- 页面不出现无接口支持的功能入口或虚假数据；
- 桌面端布局清晰、紧凑，窄屏可完成基础操作；
- 接口错误、空状态和加载状态都有明确反馈；
- 测试、类型检查和生产构建通过；
- README 说明安装、启动、环境变量和联调方式。
